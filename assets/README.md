# Изображения и публикация

`assets/images` содержит только изображения, которые использует сайт сейчас.
У каждой используемой ссылки выбран самый маленький из проверенных вариантов
с одинаковыми пикселями, размерами, цветом и прозрачностью. Дополнительное
сжатие с потерями обычно не применяется; отдельное исключение для главного
рендера описано ниже. Иконки браузера сохраняют требуемые PNG/ICO
форматы. JPG и прозрачный PNG одной планировки не считаются эквивалентными.

```text
assets/
  images/                          # Только файлы для сайта
    shared/                        # Логотип, иконки, карта, заглушки
    site/                          # Фотографии сайта
    projects/
      tchaikovsky/
        apartments/{plans,previews}/
        commercial/{plans,previews}/{a,b,c}/
        floors/{backgrounds,overlays}/
        ui/
      vivaldi/
        apartments/{plans,previews}/
        floors/backgrounds/
  manifests/production-images.json # Проверяемый список публичных файлов
  sources/                         # Локальные материалы; исключены из Git
    originals/                     # Исходники и альтернативные форматы
    project-exports/                # Дополнительные экспорты квартир
    projects/tchaikovsky/illustrator/
    unavailable-apartments.zip      # Изображения и данные 95 недоступных квартир
    catalogs/before-production.json # Полные каталоги до разделения
    data/                          # Исходные данные этажей и инструкции
    legacy-code/                   # Неиспользуемые JS/CSS и прежняя миграция
    generated/                     # Результаты обработки для ручной проверки
```

Все 403 записи Tchaikovsky и 60 записей Vivaldi сохранены. Недоступные квартиры
остаются серыми и не открываются на плане; их runtime-поля изображений используют
общую заглушку. Оригинальные изображения и ссылки сохранены в локальном ZIP и
полном снимке каталога. В ZIP проверены CRC и SHA-256 каждого файла.

## Сборка для публикации

```sh
python3 -B scripts/generate-home-routes.py
python3 -B scripts/build-production.py --check
node --test tests/*.test.mjs
python3 -B scripts/build-production.py
python3 -B scripts/build-production.py --archive dist.zip
```

Команда без параметров создаёт `dist/`; `--archive` создаёт готовый `dist.zip`
непосредственно из проверенного списка файлов. Загружать на сервер нужно содержимое
этой папки или ZIP: страницы сайта и маршрутов разделов, используемые JS/CSS, шрифты и файлы
из проверенного списка изображений. Исходники, ZIP, архив, тесты, инструменты,
документация, манифесты проверки и служебные файлы в сборку не попадают.
Непустая папка результата не перезаписывается; для повторной сборки укажите
новую папку через `--output` или предварительно перенесите прежний результат.
ZIP также не перезаписывается. Файлы Finder и прочие служебные файлы не включаются
в ZIP, даже если операционная система добавит их в локальную папку `dist` позже.

Сборка включает корневые `robots.txt`, `sitemap.xml` и `.htaccess`. При ручной
загрузке проверьте, что клиент показывает скрытые файлы. Если на Apache или
LiteSpeed уже есть `.htaccess`, добавьте в него правила из сборки, сохранив
настройки хостинга. Правила перенаправляют запросы страниц на
`https://evolutionresidence.rs` и сохраняют путь и параметры, кроме явных
`/index.html` и `/en/index.html`, которые ведут на `/` и `/en/` соответственно.

## Отправка заявок

Обе формы отправляют заявки из браузера напрямую в Bitrix24 методом
`crm.lead.add`. PHP и промежуточный обработчик не используются и не входят
в сборку. В заявке сохраняются контакты, выбранный дом и данные помещения.

Настроенный адрес хранится в локальном `config/lead-settings.local.js`,
который исключён из Git. Формат файла:

```js
export const directLeadWebhookUrl = "https://YOUR-PORTAL.bitrix24.ru/rest/USER/KEY/crm.lead.add.json";
```

Сборщик автоматически подставляет эту настройку в `js/lead-settings.js`
в готовой папке или ZIP. Повторная сборка сохраняет тот же способ отправки.
Исходный `js/lead-settings.js` содержит пустое значение; без настроенного адреса
форма сообщает о недоступности отправки и никуда не отправляет данные.

Успех показывается только после ответа Bitrix24 с номером созданного лида.
Во время отправки повторное нажатие блокируется; при ошибке введённые данные
сохраняются для повторной попытки. Локальные проверки используют тестовый адрес
и подставные ответы CRM, реальные заявки не создаются.

```sh
npm run test:e2e -- tests/e2e/forms.spec.mjs
```

## Маршруты главной

Адреса `/about-project/`, `/features/`, `/infrastructure/`, `/financing/`, `/gallery/`,
`/contact/` и `/request-callback/` открывают соответствующие разделы главной
без хэштега. У каждого адреса есть статическая HTML-страница, поэтому обновление
и прямое открытие работают на GitHub Pages, в том числе внутри `/evolution/`.
Все страницы используют метаданные и canonical главной.

Источник содержимого — `index.html`, карта маршрутов — `config/site-routes.json`.
После изменения главной или карты запустите `scripts/generate-home-routes.py`:
он обновит страницы маршрутов и `js/home-routes.js`. Генерируемые HTML нужно
коммитить вместе с исходной главной. Сборка отклоняет устаревшие копии;
отдельная проверка: `python3 -B scripts/generate-home-routes.py --check`.

Генератор также обновляет английские страницы главной, её разделов и каталога
в `en/`. Тексты берутся из `js/languages/languages.js`, английские заголовки
и описания для поиска — из `config/seo-locales.json`. Страницы отдельных
домов на обоих языках редактируются напрямую в папках каталогов домов.

При входе на главную и её маршруты удаляются только параметры фильтра каталога
(`house`, `type`, `floor`, `property`, `view`, `kvadrati-od`, `stanovi-do`).
UTM и другие независимые параметры сохраняются. Ссылки самого каталога с фильтрами
продолжают работать. Прежние `?section=...` и хэштеги известных разделов
преобразуются в соответствующие маршруты.

Выбранный дом сохраняется отдельно от URL в `sessionStorage` текущей вкладки
с ключом для текущей папки сайта. Определение дома находится в
`js/house-context.js`: контекст объекта имеет приоритет перед текущим каталогом,
URL и последним сохранённым выбором. Общая заявка и запрос цены включают
`Objekat: Tchaikovsky` или `Objekat: Vivaldi` в CRM-поле `COMMENTS`.
Если посетитель главной ещё не выбрал дом, общая заявка содержит
`Objekat: Nije izabran`.

## Очередь загрузки изображений

Бинарные изображения и их качество остаются прежними. У фотографий в HTML
заданы фактические размеры и асинхронное декодирование. Первый экран главной
загружается сразу, основная фотография имеет высокий приоритет; нижние блоки
используют нативную отложенную загрузку. Браузер может заранее подгружать
близкие к экрану изображения в зависимости от соединения.

Рендер первого экрана `site/hero/aerial-compact.webp` имеет исходные 1099×783
и весит 983 698 байт, меньше 1 МБ. Чтобы выполнить этот предел, перед lossless-WebP
кодированием убран младший бит RGB: каждый цветовой канал отличается от PNG
не более чем на 1 из 255, PSNR — 50,73 дБ. Это почти без потерь, а не точная
копия исходных пикселей. Исходный PNG сохранён в локальных материалах.
Для небольших экранов есть версия шириной 780 пикселей, также с lossless-кодированием.
Для наложения надписи за зданием применяется маска из alpha-канала присланного
SVG: `wordmark-cutout.webp`, всего 994 байта. Фон вместе с маской занимает
984 692 байта; отдельная тяжёлая фотография переднего плана не нужна.
От 768 пикселей композиция масштабируется по геометрии SVG 1920×783 и
центрируется по высоте первого экрана. Мобильный экран использует полноэкранную
фотографию и текстовую версию заголовка. Прежние фон и слой здания удалены из публичных файлов.
Полноэкранная галерея перед формой содержит десять кадров в порядке SVG-макета.
Первые шесть доступны в WebP шириной 800, 1280 и 1920 пикселей.

Обновление качества от 25 ноября: новые фотографии главной и первые шесть
кадров галереи перекодированы из исходников в lossless WebP. Уменьшенные
версии сохраняют все пиксели после Lanczos-масштабирования; повторного
сжатия с потерями нет. Для больших экранов добавлены исходные JPEG шириной
2200 пикселей, а для верхнего вида Vivaldi — 2400 пикселей. Их entropy-кодирование
оптимизировано без изменения декодированных пикселей: 22 849 483 → 20 421 292
байт. Проверки RGB и параметры обработки записаны в манифест.
У кадров 12 и 14 версия 1920 пропущена: полноразмерный JPEG выгоднее по
соотношению размера и детализации. Выбор разрешения галереи учитывает
реальный размер изображения при `object-fit: cover`, включая высокие экраны.
Прежний лимит 1 МБ на пару фотографий заменён приоритетом качества;
lossless-версии тяжелее прежних WebP q91/q93, а `srcset` сохраняет загрузку
меньших вариантов на небольших экранах.

Видеоблок после первого экрана удалён вместе с анимацией его увеличения.
Исходный ролик сохранён в проекте, но главная его не загружает, а сборка
не включает видео и его загрузчик в готовую папку или ZIP.

В сетке каталогов первая строка карточек имеет высокий приоритет, остальные
изображения остаются отложенными. Фоновые планы загружаются после выбора
режима плана: сетка Tchaikovsky больше не запрашивает начальный SVG/фон
на 1,22 МБ, а сетка Vivaldi — семь фонов на 1,56 МБ. На плане Vivaldi
загружается только выбранный этаж; прежний остаётся виден до декодирования
нового. Загруженные этажи используются повторно, неуспешные запросы можно
повторить. Полные планировки квартир по-прежнему загружаются при выборе
объекта, а модальное окно ждёт готовности изображения.

## Обновление изображений

Все 28 планов из `A3 Commercial 2D` сопоставлены с коммерческими помещениями
Tchaikovsky по номеру: A01–A07, B08–B12, B19–B28 и C13–C18. Таблица ссылок —
`js/apartments/tchaikovsky-commercial-images.js`; файлы находятся в
`assets/images/projects/tchaikovsky/commercial/{plans,previews}/{a,b,c}/`.
Полные планы сохраняют исходные пиксели, размеры, цветовые профили и ориентацию:
63 717 733 → 32 363 910 байт (−49,2%). Для карточек используются отдельные
превью в пределах 640×640 без обрезки, суммарно 1 122 106 байт. Модальное окно
загружает полный план и показывает весь лист через `object-fit: contain`.

Инструменты обработки читают локальные исходники, а результаты записывают в
`assets/sources/generated`. Они не меняют публичные изображения и runtime-код.
После проверки качества нужно перенести выбранный результат в `assets/images`,
обновить готовые URL и список `production-images.json`, затем повторить сборку.
Восстановление недоступной квартиры начинается с распаковки её файлов из ZIP;
данные и прежние ссылки находятся в `catalog.json` внутри архива.
